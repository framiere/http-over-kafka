Put Kafka under your HTTP services. Change nothing in them.

http-over-kafka carries the calls between your microservices through Kafka. Callers still get the real response. Services still receive plain HTTP. And every order placed, payment taken or address changed becomes a real-time stream the rest of your company can build on.

Your business already happens over HTTP. Kafka doesn't see it.

The data that matters flows through request and response, then disappears. Getting it into Kafka usually means one of three projects.

ApproachWhat it costsWhat you still miss
Rewrite services to publish eventsA Kafka client, an outbox and a schema in every service, team by team, for monthsEvery service not rewritten yet
Change data capture on each databaseAccess to every team's database and a connector per storeWho called, which operation, and every request that failed
Log traffic from the API gatewayLittle: a pluginCompleteness. Logs are batched and dropped when Kafka is slow
http-over-kafkaA gateway in front, a bridge per service, an OpenAPI file you already haveServices and teams keep working exactly as before

What stays the same

  • Your services keep their code, their frameworks and their deployments. No Kafka client.
  • Callers keep sending HTTP and get the service's real status, headers and body.
  • GET requests go straight to the service. Kafka never sees them.
  • Moving a service in or out is a route change. You can go back the same way.

What you gain

  • A durable, replayable stream of every mutation, with who called and what happened.
  • Business events like OrderCreated, declared in OpenAPI, published as they happen.
  • New consumers (analytics, search, fraud, AI agents, audit) without asking the owning team.
  • Safer side effects: one execution per request, idempotent retries, signed records.

How a request crosses Kafka

For the caller the call stays synchronous. Underneath, the request is written to Kafka before the service is touched, so nothing can happen without leaving a trace.

  1. The caller sends plain HTTP

    The gateway checks the caller's token, finds the operation in the service's OpenAPI and strips secrets like Authorization.

  2. The command is written first

    A signed command lands in http.requests.orders, acknowledged by Kafka before anything else happens.

  3. The bridge calls your service, once

    It records that the call is starting, then sends an ordinary HTTP request. Your service never knows Kafka was involved.

  4. Response and result are stored together

    One Kafka transaction holds the response, the result (CreateOrderSucceeded) and the deduplication state.

  5. The caller gets the real answer

    Same status, same headers, same bytes. Meanwhile the deriver publishes OrderCreated if your OpenAPI declares it.

What happens when things break

Putting Kafka between two services is easy. Not charging a card twice when a process dies halfway is the actual work. These are the answers a caller gets, and whether the service runs.

We tried hard to break it

The end-to-end suite builds the real binaries and attacks them: processes killed and frozen at random, Kafka paused, partitions added, state wiped, records forged. The payment service's own debit counter is the judge.

Writing it uncovered five ways to debit a card twice, all through operator actions. Each one is fixed and has a regression test.

Get started in four steps

  1. Run the demo stack

    Kafka, two demo services, the gateway, the bridges, the deriver and the audit consumer. Requires Docker and Go 1.26.

    git clone https://github.com/sderosiaux/http-over-kafka
cd http-over-kafka
make up
./scripts/demo.sh

  2. Put one of your services behind the gateway

    Register it with the gateway and give both the gateway and its bridge the service's OpenAPI file. Callers switch to the gateway's hostname.

    # gateway
HOK_SERVICES=orders=http://orders:8081
HOK_SPEC_DIR=/specs        # contains orders.openapi.yaml

# bridge, one per service
HOK_SERVICE=orders
HOK_UPSTREAM=http://orders:8081

  3. Declare the events you care about

    A few lines in the OpenAPI file. The event is published only when the service actually answers 201.

    post:
  operationId: createOrder
  x-conduktor-event:
    on: 201
    topic: orders.events
    type: OrderCreated
    key: $.response.body.id
    value:
      id: $.response.body.id
      customerId: $.request.body.customerId
      items: $.request.body.items

  4. Subscribe from anywhere

    Events are CloudEvents with the request ID as ce_id. Any Kafka consumer can read them, now or later.

    kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders.events --from-beginning \
  --isolation-level read_committed \
  --property print.headers=true

Where it stands

The project is experimental. It is built to evaluate the approach on real services, and it is honest about what is not done yet.

Read all the limits and design decisions

  • Kafka is in the write path: if Kafka is down, mutations fail and reads keep working.
  • No double execution relies on callers retrying with an Idempotency-Key.
  • Not yet measured on a multi-broker cluster with three replicas.
  • No WebSocket, server-sent events, streaming bodies or multipart.

Shape what comes next

Every change starts as an issue or a pull request. Pick something from the roadmap, propose your own, or tell us how you would use it.
